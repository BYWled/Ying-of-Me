问题汇总

一、 组件基础与架构演进

1. 主问：类组件 (Class Component) 与 函数式组件 (Functional Component) 有什么本质区别？

  • 追问 1：为什么现在前端社区和官方都全面推崇函数式组件？Hooks 究竟解决了类组件的什么痛点？
  • 追问 2：useState 触发的更新属于宏任务还是微任务？函数组件又是如何利用 useEffect 完美替代类组件生命周期的？其闭包陷阱（Capturing Value）的本质原因是什么？
参考答案&简要代码

1. 本质区别

  • 心智模型：类组件是面向对象编程（OOP）的体现，依赖 this 指向和实例状态；函数组件是函数式编程（FP）的体现，主打“输入驱动输出”（$UI = f(state)$），本质是一个纯函数。
  • 内存与底层机制：类组件在 React 内部需要经历实例化过程，生命周期和状态挂载在组件实例（this）上；而函数组件每次渲染（Render）都会重新执行整个函数，其状态和副作用通过 Hooks 闭包保存在与之对应的 Fiber 节点的 memoizedState 链表上。

2. Hooks 解决的类组件痛点

  • 状态逻辑复用困难：类组件过去只能靠高阶组件（HOC）或 Render Props 来复用状态逻辑，容易陷入“嵌套地狱”（Wrapper Hell），使组件树层级过深。Hooks 允许将状态逻辑提取到独立的自定义 Hook 中。
  • 巨石组件难以维护：类组件的逻辑被迫按照生命周期割裂（例如在 componentDidMount 和 componentWillUnmount 中同时写定时器的监听与解绑），而 Hooks 可以将相关的逻辑聚合在一起。
  • this 指向困扰：类组件中需要频繁绑定 bind(this)，一旦漏写极易引发指向错误。

3. 追问 2 深度剖析

  • useState 的更新归属：
    • 这是一个高频陷阱题。useState 触发的更新既不属于原生的宏任务，也不属于微任务，它是 React 自身调度系统（Scheduler）管理的用户交互任务。
    • 在内部，React 会将多次 useState 调用放进更新队列中（Batching 批处理）。
    • 在当前事件循环的同步代码执行完后，React 调度系统会利用微任务（如 queueMicrotask 或 Promise.resolve）或者宏任务（在不支持微任务或在低版本下利用 MessageChannel，取决于 React 的版本和并发模式）去触发 Fiber 树的 Reconciliation（调和）与重新渲染。
  • useEffect 替代生命周期：
    • useEffect(cb, []) 类似 componentDidMount。
    • useEffect(cb, [deps]) 类似 componentDidUpdate。
    • useEffect(() => cb, []) 返回的清理函数类似 componentWillUnmount。
  • 闭包陷阱（Capturing Value）的本质：
    • 函数组件在每次 Render 时都会形成一个全新的闭包。在这个闭包里，所有的 state 和 props 都冻结在“当前渲染”的那一刻。
    • 如果我们在异步回调（如 setTimeout）中读取旧状态，拿到的依然是触发该异步操作时的那一帧状态。
    • 解决方案：
      1. 使用 useRef 保存状态（因为 ref.current 始终指向同一个内存地址）。
      2. 使用 useState 的函数式更新：setState(prev => prev + 1)。

2. 主问：谈谈你对受控组件与非受控组件的理解，实现一个受控 Input 的关键点是什么？

  • 追问 1：原生 DOM 事件对象与 React 合成事件（SyntheticEvent）对象有何区别？React 为什么要多此一举设计合成事件？
  • 追问 2：【手写实战】请用 React 原生 Hooks 实现一个通用的弹窗组件（Dialog/Modal），要求支持 title、children 自定义内容以及 onClose 关闭回调。
参考答案&简要代码

1. 受控与非受控组件

  • 受控组件：表单元素的值完全由 React 的 state 控制，必须通过 value 属性绑定 state，并通过 onChange 事件监听用户输入，再同步更新 state。
  • 非受控组件：表单元素的值由 DOM 节点自身管理，React 使用 useRef 直接在需要时去获取 DOM 节点以提取数据。
  • 受控 Input 关键点：
    • 必须显式声明 value={state}。
    • 必须绑定 onChange={(e) => setState(e.target.value)}。
    • 要避免由于 value 为 undefined 导致组件在受控与非受控状态间切换报错（应提供兜底值 value={state || ''}）。

2. 原生 DOM 事件 vs React 合成事件

  • 底层区别：
    1. 挂载位置不同：原生事件直接挂载在真实 DOM 上；而 React 合成事件并不直接挂载到每个真实 DOM 节点，在 React 17 之后，它们被统一绑定在应用的根容器（Root Container，如 #root）上。
    2. 事件机制不同：React 内部实现了一套事件冒泡和捕获机制，并在根节点进行事件分发（Event Distribute）。
    3. 对象不同：React 传递给回调的是经过封装的 SyntheticEvent，该对象符合 W3C 标准，跨浏览器兼容性极佳。
  • 为什么要设计合成事件：
    • 跨平台兼容性：抹平不同浏览器之间的差异（例如 transitionend、animationend 等）。
    • 性能优化：通过事件委托（Event Delegation）机制，避免了在每个子 DOM 元素上重复绑定监听器，极大降低了内存消耗。
    • 配合 Fiber 与并发模式：合成事件方便 React 调度系统对其进行优先级标记，从而更好地支持中断与批处理（Batching）。

二、 状态管理与数据流转

3. 主问：React 的状态更新机制是什么？useState 与 Redux 中的全局状态有什么本质区别？

  • 追问 1：Redux 中的变量变化后，页面为什么能自动渲染？它的核心触发机制（如 useSelector）是如何感知状态改变并通知 React 重新执行的？
  • 追问 2：请横向对比 Redux、Dva、Zustand、Jotai 等状态管理库，在真实中大型项目落地中，状态管理的划分原则（Local State vs Global State）是怎样的？
参考答案&简要代码

1. React 状态更新机制与区别

  • 状态更新机制：React 的状态更新基于“单向数据流”和“不可变数据（Immutability）”。状态变化时，会调用 setState/dispatch，在当前 Fiber 树上创建一个 Update 对象并挂载到待处理队列，然后触发 React 的调和与 Diff 过程，生成新的 Virtual DOM 并打补丁渲染到真实 DOM。
  • 本质区别：
    • useState 是组件局部状态。状态存储在当前组件对应的 Fiber 节点的 memoizedState 属性中，生命周期随组件销毁而销毁。
    • Redux 是应用全局状态。状态存储在内存中的一个单一 Store（JS 对象）里，与 React 组件树完全脱离，生命周期贯穿整个应用的生命周期。

2. Redux 变量变化触发渲染的底层原理

Redux 的状态更新和 React 渲染本来是独立的，之所以能联动，全靠 react-redux 库架设的桥梁。

  • Redux 核心流转过程：
    1. 调用 store.dispatch(action) $\rightarrow$ 触发 reducer $\rightarrow$ 计算出全新的 state。
    2. react-redux 内部通过 store.subscribe(listener) 注册了订阅器。当 Store 状态改变，所有的订阅 listener 被触发。
  • useSelector 的核心感知机制：
    • useSelector 内部通过 React 的 useSyncExternalStore（React 18）或底层的 useReducer/useState 维持了一个用于强制更新的 forceUpdate 标记。
    • 在订阅函数触发时，useSelector 会获取最新的 storeState，并利用传入的 selector 函数计算出你选择的切片值。
    • 它将新计算的值与上一次缓存的值进行浅比较（Shallow Compare）。
    • 若发现值变了，就会触发 forceUpdate()，使当前组件重新 Render；若没变，则直接拦截，防止不相关的全局状态修改导致无关组件重绘。

3. 常见状态管理库横向对比

状态管理库 状态心智模型 状态更新范式 优点 缺点 / 适用场景
Redux 单一数据源，全局树 不可变数据，dispatch(action) 极其严格、可预测、单向流，调试工具强大 样板代码极多（Action/Reducer），适合超大型、规范度要求极高的项目
Dva 基于 Redux 基于 Redux-saga 的数据流整合方案 内置副作用处理（Effects），开发体验较好 社区活跃度降低，逐渐被现代工具取代

Jotai 原子化状态（Atom） 响应式/细粒度更新（类似 Vue） 极其精确的局部重绘，状态细粒度拆分，无冗余重绘 原子管理复杂时结构零散，适合高频交互、局部状态高联动的场景

4. 中大型项目状态划分原则

在落地中，应严格遵循“状态就近原则”：

  1. Local State（组件私有状态）：如弹窗的开关（isOpen）、输入框临时内容（inputValue）、仅限当前页面使用的分页参数（pageNum）。绝不放入全局。
  2. Global State（全局共享状态）：跨页面、多组件深度嵌套共享的数据。如用户信息、全局权限路由、购物车列表、系统全局配置。
  3. Server State（服务端缓存状态）：通过 React Query 或 SWR 管理，将接口返回的数据作为缓存处理，不污染全局 UI 状态。

三、 性能优化与 Hook 底层原理

4. 主问：谈谈你对 useCallback 和 useMemo 的理解与使用场景？何时不应该使用它们？

  • 追问 1：React Fiber 架构下，Hooks 是如何存储在 Fiber 节点上的？为什么不能在 if 或循环中调用 Hooks？
  • 追问 2：在实际项目中，除了这两个 Hooks，你还用过哪些前端性能优化的实战手段？（要求结合瀑布流虚拟列表、下拉刷新防二次请求等真实场景）。
参考答案&简要代码

1. useCallback 与 useMemo

  • 本质区别：
    • useCallback(fn, deps) 缓存的是函数引用本身。
    • useMemo(() => val, deps) 缓存的是函数执行后返回的值。
  • 何时不该使用（高频误区）：
    • 不要闭眼到处使用！useCallback 和 useMemo 本身也是有计算和内存开销的。每次渲染，React 都需要创建新依赖数组、做依赖项浅比较、在内存中存储前一次的函数/值。
    • 若传递给子组件的是普通原生元素（如 <button onClick={cb}>），使用 useCallback 属于无意义消耗。
    • 何时该用：
      1. 传递给子组件的函数，且该子组件被 React.memo 包裹进行性能拦截。
      2. 函数或计算值作为其他 Hooks（如 useEffect）的依赖项。
      3. 极其昂贵的 CPU 计算逻辑（如过滤几万条数据的过滤算法）。

2. Hooks 存储结构与不能在条件句中使用的底层原因

  • 存储结构：

    • 每个 React 组件对应一个 Fiber 节点。

    • Fiber 节点上有一个 memoizedState 属性。在函数组件中，它存的不是普通的 state，而是一个单向链表。

    • 链表的每个节点（Hook 对象）对应一个 Hook 的调用次序，格式类似：

    • React 在更新阶段，是完全依赖 Hook 的调用顺序（即链表的指针移动指针 next）来将当前的 state 状态与上一次的值匹配起来的。
    • 如果把 Hook 写在条件句中，导致某次渲染时其中一个 Hook 没有执行，整个链表节点的访问顺序就会发生错乱，后面的 Hook 读取到的就是前一个 Hook 的历史状态，从而引发灾难性的 Bug。React 团队通过 ESLint 插件强制规定此规则。

3. 前端性能优化实战手段（结合面经热点）

  • 场景 1：瀑布流虚拟列表（Virtual List）实现思路：
    • 在加载海量图片瀑布流时，直接渲染全部 DOM 导致页面卡顿死机。
    • 实现思路：
      1. 容器监听 onScroll。
      2. 根据视口高度 clientHeight 和当前滚动距离 scrollTop，动态计算出当前可视区应该渲染的 item 范围（如 [start, end]）。
      3. 用绝对定位（absolute）将可视区内的 DOM 渲染出来，并加上对应的 top 偏移。
      4. 未在可视区的内容只保留空的占位容器高度，减少 90% 以上的真实 DOM 渲染，解决卡顿。
  • 场景 2：下拉刷新遇到刷新两次问题（艾未恩面经高频）：
    • 原因分析：往往是因为没有做防抖/节流控制，或者手势触发（touchmove / touchend）判定距离不明确，导致在网络请求返回前重复触发了接口。
    • 解决思路（双重防御）：
      1. 引入状态锁 loading，一旦开始请求，直接置为 true，拦截后续的刷新信号。
      2. 为请求提供唯一标识，或者结合 AbortController 在第二次刷新动作触发时，直接 cancel 掉上一次未完成的请求。

四、 TypeScript 与 React 实战进阶

5. 主问：TypeScript 中 type 和 interface 的本质区别是什么？

  • 追问 1：在声明 React Props 和函数组件时，你会优先选用哪一个？如何利用 TS 约束一个组件支持任意泛型？
  • 追问 2：对泛型工具 Pick 的底层源码实现有何理解？此外，TypeScript 中的 unknown 和 never 有什么区别，分别在什么业务场景下使用？

1. type vs interface

  • 扩展方式（主要区别）：
    • interface 通过 extends 进行扩展；且支持声明合并（Declaration Merging），在不同地方重复声明同名 interface，TS 会自动将其属性合并。
    • type 通过交叉类型 & 进行扩展；不支持声明合并，重复定义会直接报错。
  • 能力范围：
    • type 表达能力更强，可以声明基本类型别名、联合类型（Union）、元组（Tuple）以及进行复杂条件类型计算。
    • interface 只能声明对象、函数和类的形状。

2. React 实战选型与泛型组件约束

  • 团队规范与选型：
    • 日常组件的 Props 定义优先使用 interface（方便其他模块或三方库继承扩展）。
    • 遇到需要使用联合类型（如 type Theme = 'light' | 'dark'）或需要进行映射类型处理时，使用 type。
  • React 泛型组件应用：
    • 常见场景：通用的下拉选择框（Select）、表格（Table），数据项的 value 或 record 格式是不确定的。

  • 解析：
    • keyof T 获取 T 的所有属性键组成的联合类型。
    • K extends keyof T 约束传入的要挑选的键 K 必须是 T 已有的属性子集。
    • [P in K] 是映射类型，遍历联合类型 K 中的每一个属性 P。
    • T[P] 为类型索引访问，获取对应属性的具体类型。

4. unknown vs never

  • unknown（安全未知类型）：
    • 是所有类型的Top Type（任何类型都可以赋值给 unknown）。

    • 场景：用于处理后端返回的格式不确定的不安全数据，或者编写高度通用的底层库（如 Axios 响应体拦截器、全局 Loading 拦截器等）。

五、 跨端、跨框架与调和

6. 主问：React 和 Vue 在底层的数据绑定与更新原理上有什么本质区别？

  • 追问 1：React 的虚拟 DOM (Virtual DOM) 是怎么生成的？它的 Diff 算法与 Vue 的双端 Diff / 快速 Diff 有什么不同？
  • 追问 2：在跨端方案中，Uniapp 和 Taro 各有什么特点？为什么在中大型跨端项目中，不少团队更倾向于选用 Taro？
参考答案&简要代码

1. 数据绑定与更新原理区别

  • React：单向数据流 + 显式状态更新
    • 数据单向流转。更新依赖显式调用 setState，React 本身对具体哪个数据发生了变化“一无所知”。
    • 它采用粗粒度的更新策略：一旦组件状态改变，React 会自顶向下重新执行该组件及其所有子组件的渲染逻辑。
    • 必须通过虚拟 DOM 进行调和与 Diff 算法对比，找出差异后再打补丁到真实 DOM（可以通过 useMemo 或 React.memo 做手动阻断优化）。
  • Vue：响应式劫持 + 依赖收集（双向数据绑定）
    • 使用 Object.defineProperty (Vue2) 或 Proxy (Vue3) 对数据进行属性劫持。
    • 它采用细粒度的更新策略：组件渲染时会自动触发 getter 进行依赖收集（Collect Dependency），将当前的副作用函数（Render Watcher/Effect）与数据键绑定。
    • 一旦数据变化，触发 setter 精准派发更新，直接告知 Reactivity 系统哪些组件发生了变化，从而只对变化了的组件进行局部精准渲染。

2. 虚拟 DOM 生成与 Diff 算法大厂对比

  • 虚拟 DOM 生成：
    • 在 React 中，我们写的 JSX 经由 Babel 编译，转化为 React 17+ 的 _jsxRuntime.jsx(...) 或低版本的 React.createElement(...) 函数调用。
    • 这些函数执行后，会返回一个描述 DOM 结构的普通 JS 对象（即 Virtual DOM）。
  • Diff 算法差异：
    • React Diff（单端/单向遍历）：
      • 为了降低计算成本，React 做出了三大假设：相同层级节点对比；不同类型组件产生不同树；通过 key 识别移动。
      • 算法过程：只做单向从左到右遍历。
        • 第一轮遍历：尝试复用新旧节点中位置没有发生改变的节点。一旦遇到不能复用的，终止遍历。
        • 第二轮遍历：将剩余旧节点放入一个以 key 为键的 Map 中，然后遍历新节点，从 Map 中查找复用。通过对比新旧节点在旧树中的索引 lastPlacedIndex，决定节点是插入、删除还是移动。
    • Vue2 Diff（双端指针）：
      • 采用双端指针算法（头头、尾尾、头尾、尾头四路对比）。从两端向中间收拢，在处理“首尾互换”、“倒序”等场景下，比起 React 的单向对比，能够显著减少真实 DOM 的移动次数。
    • Vue3 Diff（快速 Diff / 最长递增子序列）：
      • 借鉴了 ivi 和 inferno 算法。
      • 首先自前向后、自后向前进行相同节点的预处理。
      • 对于中间乱序部分，Vue3 建立了一个“新旧节点位置映射表”，并利用“最长递增子序列（LIS）”算法计算出不需要移动的节点索引。只对处于子序列之外的节点进行移动，达到了最少移动 DOM 的极致性能。

3. 跨端方案对比：Uniapp vs Taro

  • 开发心智与技术栈：
    • Uniapp：基于 Vue 生态。对于习惯 Vue 语法的开发者极为友好，开发上手简单，生态和组件库在小程序端非常庞大。
    • Taro：由京东凹凸实验室开发，主要支持 React 技术栈（虽然目前也兼容 Vue，但 React 仍是主流生态）。
  • 多端一致性与架构优势：
    • Uniapp 的重心在于微信小程序的高效输出，对于多端（Web, App, H5）的细节抹平在大型复杂业务中可能存在兼容性缺陷。
    • Taro 在设计之初就高度重视多端一致性。它通过高度重构的编译时（利用 Babel 转换 React JSX 代码为小程序模板）和强大的运行时（劫持小程序 DOM/BOM 接口）设计，使得在多端代码编译时表现得极其稳定。
  • 为什么中大型项目更倾向于 Taro：
    • 逻辑复用性：React 的 Hooks 设计使得非 UI 的纯业务逻辑复用率高达 95% 以上，且无需考虑 Vue 复杂的 watch/computed 依赖链路。
    • 大型团队协作与 TS 契合度：React 技术栈天然与 TypeScript 完美契合，配合 Taro 能够实现完美的静态类型检查。这对于数十人协作、维护周期长达数年的中大型复杂跨端项目来说，能极大地降低线上故障率，保证代码的高可维护性。

        1. 1. 本质区别 心智模型：类组件是面向对象编程（OOP）的体现，依赖 this 指向和实例状态；函数组件是函数式编程（FP）的体现，主打“输入驱动输出”（$UI = f(state)$），本质是一个纯函数。 内存与底层机制：类组件在 React 内部需要经历实例化过程，生命周期和状态挂载在组件实例（this）上；而函数组件每次渲染（Render）都会重新执行整个函数，其状态和副作用通过 Hooks 闭包保存在与之对应的 Fiber 节点的 memoizedState 链表上。 2.     2. 二、 状态管理与数据流转
      1. 3. 主问：React 的状态更新机制是什么？useState 与 Redux 中的全局状态有什么本质区别？

React 状态更新机制与区别 状态更新机制：React 的状态更新基于“单向数据流”和“不可变数据（Immutability）”。状态变化时，会调用 setState/dispatch，在当前 Fiber 树上创建一个 Update 对象并挂载到待处理队列，然后触发 React 的调和与 Diff 过程，生成新的 Virtual DOM 并打补丁渲染到真实 DOM。 本质区别： useState 是组件局部状态。状态存储在当前组件对应的 Fiber 节点的 memoizedState 属性中，生命周期随组件销毁而销毁。 Redux 是应用全局状态。状态存储在内存中的一个单一 Store（JS 对象）里，与 React 组件树完全脱离，生命周期贯穿整个应用的生命周期。 2.       1. 4. 主问：谈谈你对 useCallback 和 useMemo 的理解与使用场景？何时不应该使用它们？

      1. 6. 主问：React 和 Vue 在底层的数据绑定与更新原理上有什么本质区别？
        1. 1. 数据绑定与更新原理区别 React：单向数据流 + 显式状态更新 数据单向流转。更新依赖显式调用 setState，React 本身对具体哪个数据发生了变化“一无所知”。 它采用粗粒度的更新策略：一旦组件状态改变，React 会自顶向下重新执行该组件及其所有子组件的渲染逻辑。 必须通过虚拟 DOM 进行调和与 Diff 算法对比，找出差异后再打补丁到真实 DOM（可以通过 useMemo 或 React.memo 做手动阻断优化）。 Vue：响应式劫持 + 依赖收集（双向数据绑定） 使用 Object.defineProperty (Vue2) 或 Proxy (Vue3) 对数据进行属性劫持。 它采用细粒度的更新策略：组件渲染时会自动触发 getter 进行依赖收集（Collect Dependency），将当前的副作用函数（Render Watcher/Effect）与数据键绑定。 一旦数据变化，触发 setter 精准派发更新，直接告知 Reactivity 系统哪些组件发生了变化，从而只对变化了的组件进行局部精准渲染。 2. 虚拟 DOM 生成与 Diff 算法大厂对比 虚拟 DOM 生成： 在 React 中，我们写的 JSX 经由 Babel 编译，转化为 React 17+ 的 _jsxRuntime.jsx(...) 或低版本的 React.createElement(...) 函数调用。 这些函数执行后，会返回一个描述 DOM 结构的普通 JS 对象（即 Virtual DOM）。 Diff 算法差异： React Diff（单端/单向遍历）： 为了降低计算成本，React 做出了三大假设：相同层级节点对比；不同类型组件产生不同树；通过 key 识别移动。 算法过程：只做单向从左到右遍历。 第一轮遍历：尝试复用新旧节点中位置没有发生改变的节点。一旦遇到不能复用的，终止遍历。 第二轮遍历：将剩余旧节点放入一个以 key 为键的 Map 中，然后遍历新节点，从 Map 中查找复用。通过对比新旧节点在旧树中的索引 lastPlacedIndex，决定节点是插入、删除还是移动。 Vue2 Diff（双端指针）： 采用双端指针算法（头头、尾尾、头尾、尾头四路对比）。从两端向中间收拢，在处理“首尾互换”、“倒序”等场景下，比起 React 的单向对比，能够显著减少真实 DOM 的移动次数。 Vue3 Diff（快速 Diff / 最长递增子序列）： 借鉴了 ivi 和 inferno 算法。 首先自前向后、自后向前进行相同节点的预处理。 对于中间乱序部分，Vue3 建立了一个“新旧节点位置映射表”，并利用“最长递增子序列（LIS）”算法计算出不需要移动的节点索引。只对处于子序列之外的节点进行移动，达到了最少移动 DOM 的极致性能。 3. 跨端方案对比：Uniapp vs Taro 开发心智与技术栈： Uniapp：基于 Vue 生态。对于习惯 Vue 语法的开发者极为友好，开发上手简单，生态和组件库在小程序端非常庞大。 Taro：由京东凹凸实验室开发，主要支持 React 技术栈（虽然目前也兼容 Vue，但 React 仍是主流生态）。 多端一致性与架构优势： Uniapp 的重心在于微信小程序的高效输出，对于多端（Web, App, H5）的细节抹平在大型复杂业务中可能存在兼容性缺陷。 Taro 在设计之初就高度重视多端一致性。它通过高度重构的编译时（利用 Babel 转换 React JSX 代码为小程序模板）和强大的运行时（劫持小程序 DOM/BOM 接口）设计，使得在多端代码编译时表现得极其稳定。 为什么中大型项目更倾向于 Taro： 逻辑复用性：React 的 Hooks 设计使得非 UI 的纯业务逻辑复用率高达 95% 以上，且无需考虑 Vue 复杂的 watch/computed 依赖链路。 大型团队协作与 TS 契合度：React 技术栈天然与 TypeScript 完美契合，配合 Taro 能够实现完美的静态类型检查。这对于数十人协作、维护周期长达数年的中大型复杂跨端项目来说，能极大地降低线上故障率，保证代码的高可维护性。
